HidraNet Browser 1.1.1 — SHA-256 checksums
==========================================

Verify before running.

  macOS / Linux:   shasum -a 256 <file>
  Windows:         Get-FileHash .\<file> -Algorithm SHA256

If the value does not match the table below, do not run the file.

What a match tells you: that your file is the file this table lists, and
nothing more. The table is published by the same maintainers, from the
same repository and accounts, as the files themselves: someone who could
replace the files could replace this table to match them. It does not
prove who built the file.


SIGNED RECORD
-----------------------------------------------------------------------

The browser (1.1.0 and later) reads these three lines to tell you when a
newer build is out, or when yours has known security problems. It only
tells you; it never downloads or installs anything.

  latest-version:        1.1.1
  minimum-safe-version:  1.1.0
  valid-until:           2027-05-11

It believes them only when SHA256SUMS.txt.sig, beside this file, is an
Ed25519 signature of this whole file made offline with the HidraNet
release key, the key that also signs HidraVPN. Its public half is built
into the browser and into HidraVPN, and published at hidranet.org/vpn/:

  denZsjS2YtKOo4LRIGGTaKuHIWDFigChoLa71o0jBq8=

The signature covers the label "hidranet-browser-sums-v1", a zero byte,
then this file, so it cannot be passed off as the signature of anything
else that key signs. To check it yourself with hidravpn-sign:

  { printf 'hidranet-browser-sums-v1\0'; cat SHA256SUMS.txt; } > sums.msg
  cp SHA256SUMS.txt.sig sums.msg.sig
  hidravpn-sign verify --pubkey <the key above> sums.msg

For a first download, a key read from this site is only as trustworthy as
the site. For a browser already installed, the key is built in: whoever
controls this site cannot make it believe a record the maintainers did
not sign. They can still take the record away or serve an older one. The
browser keeps the newest record it has verified and believes it until
its valid-until, and after that says it cannot confirm it is up to date.


KNOWN PROBLEMS WITH THE 1.0.0 PACKAGES
-----------------------------------------------------------------------

The 1.0.0 Linux package runs Electron 33.4.11 (Chromium 130), which no
longer receives security fixes, and Tor 15.0.22. The 1.0.0 Windows and
macOS packages were made the same way; assume the same of them. The
source they were refreshed from names Electron 44.9.3 and Tor 15.0.26,
but the runtime and Tor were carried over from an older package without
being checked against those pins. 1.1.0 was that rebuild, and 1.1.1,
listed below, follows it: both made from scratch on the pinned Electron
and Tor, each under a new version number, so the 1.0.0 names are never
given other files.

Every 1.0.0 package also has two leaks, fixed in 1.1.0. A
page can make the system look up the names it hints at (DNS prefetch)
through the system's own resolver, outside Tor: the site can learn which
resolver you use, and your network can see those names. And a tab opened
while Tor is still connecting can load without Tor, or through any other
program listening on port 9050 of this machine.

Every copy of 1.0.0 calls itself 1.0.0. Copies downloaded before
22 October 2026 also lack some or all of the security fixes made since
the first packages, among them the bridge that let any downloaded .html
file turn Tor off and the engine API that answered any website. Replace
every copy of 1.0.0 with 1.1.1. None of the 1.0.0 copies checks for
updates, so they cannot learn of this themselves.

NONE OF THESE BUILDS ARE SIGNED OR NOTARISED

There is no Apple Developer ID and no Windows code-signing certificate
behind this release. The app is unsigned — not signed badly, not signed
with something expired: unsigned. On Apple Silicon the kernel will not
load unsigned arm64 code, and macOS reports that as

    "HidraNet.app is damaged and can't be opened."

The download is not corrupt. Sign it locally and it opens:

    xattr -cr HidraNet.app
    codesign --force --sign - HidraNet.app/Contents/Resources/bin/tor/tor
    codesign --force --deep --sign - HidraNet.app
    open HidraNet.app

Tor is signed first and on its own because --deep does not descend into
Resources/. Skip that line and the app opens but cannot connect.

A matching checksum tells you that the file is the one the table lists.
It does not tell you that the maintainers built it (see the top of this
file), nor that an operating system will accept it without complaint.
See README-macOS.txt inside the macOS ZIP.
